# 每日轨迹终点漏写回归

## 原因

2026-09-10 的实际规划记录显示：日程标题包含每日公里数，但任务解释器只授权了日程、旅程地图位置和装备写入，没有授权 `set_itinerary_group_endpoints`。执行助手的工具列表因此不包含终点工具。七个已保存行程组的 `route_end_meters` 全部为空，任务仍被判断为完成。

任务 schema 同时存在“排除可选地图/终点修复”的误导性描述；解释器缺少服务端绑定轨迹的明确元数据；原覆盖校验只在用户明确给出天数时执行。

真实模型回归还复现了另一条失败路径：模型抄错轨迹地名，整批终点因精确匹配校验被拒绝，随后重试耗尽预算。不能通过接受虚构地名来修复。

## 修复

- 区分完整徒步规划与交通补充、装备和单项编辑。完整轨迹规划将每日终点作为必需依赖，不再把日程标题中的公里数当作结构化终点。
- 服务端将绑定轨迹是否存在及文件名交给解释器，不要求重新上传。仅查询两个坐标点判断轨迹存在，不传输整条轨迹。
- 完整规划入口在已经授权日程与完整装备规划时补齐终点操作依赖；讨论、无轨迹、交通及单项操作不自动扩权。
- 终点写入回执包含实际行程组数量，天数待定也需覆盖全部组并到达轨迹终点，才能判定完整保存。用户的待定天数和日期不因此改变。
- 新增 `waypointIndex` 和 `trackFinish` 选择方式，服务端直接从当前轨迹取原始名称、累计距离和坐标。摘要在新读取和缓存复用时都附带原数组编号，同名不同位置仍可区分；已有版本冲突保护避免用旧编号盲写新轨迹。旧名称/公里数方式保持严格校验。

## 验证

53 项相关 Deno 回归测试通过，覆盖任务分配、工具可见性、天数待定、局部写入不能冒充完成、非徒步操作不扩权、候选营地、标注点编号、新旧缓存、真实轨迹位置和已有装备流程。应用 TypeScript、服务端 Deno 类型检查及进度字段投影测试通过。

通用隔离测试位于 `supabase/tests/agent-track-planning.integration.ts`，不在 Edge Function 部署目录。测试读取参数指定旅程的轨迹，在临时账号下调用真实任务解释器、模型和写入工具，并逐组核对终点位置、递增距离和全轨迹覆盖，最后清理测试数据。没有写死路线、营地或天数。

```bash
env KAIPA_AI_MODEL=<model> /home/coder/.deno/bin/deno run \
  --allow-env --allow-read --allow-net \
  --env-file=../kaipa-supabase-docker/.env \
  supabase/tests/agent-track-planning.integration.ts <source-journey-id> --track-only
```

`--track-only` 限定使用已有轨迹营地标注，不搜索攻略。它验证规划保存能力，不认证实际营地或水源。首轮含攻略搜索的模型测试未在执行预算内完成，不计为通过；临时数据已清理，原旅程未改动。

采用编号选择后的真实模型验证通过：任务解释、保存日程和保存终点三个阶段正常完成，七个行程组均有终点；累计米数为 10284.79996、24242.64347、39605.47467、52030.84962、62335.73592、69710.63923、80374.40697。逐组地图坐标校验通过，日期和正式天数仍为空，中间营地保留候选标签。测试账号和旅程已清理。此结果不表示含外部搜索的全部场景都已验证，也不改写原用户旅程。
